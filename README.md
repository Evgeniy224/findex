# findex — Лабораторна 1

## Корпус
Для тестування використовується папка `data/` з 3 тестовими текстовими файлами.

## Результати вимірювань

| Версія | Документів | Токенів | Словник | Час (сек) | Пікова пам'ять (МБ) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Лінива (генератори) | 3 | 77 | 60 | 0.0018 | 0.0155 |
| Жадібна (списки) | 3 | 77 | 60 | 0.0003 | 0.0137 |

### Пояснення
На такому малому корпусі різниця в пам'яті є мінімальною, оскільки накладні витрати на сам `tracemalloc` 
перевищують обсяг даних. Однак, при зростанні корпусу (до тисяч документів), "жадібна" версія буде змушена
зберігати в памʼяті всі документи та списки токенів одночасно, що призведе до лінійного зростання споживання
памʼяті (O(N)). "Лінива" ж версія використовує генератори, тому зберігає в памʼяті лише один поточний 
документ, а памʼять зростає лише за рахунок словника `Counter`, який обмежений кількістю унікальних слів 
у мові.

# Лабораторна 2: Інвертований індекс, хешування та пам'ять

## Що було зроблено

У цій лабораторній ми перетворили наш лінивий конвеєр з Лабораторної 1 на повноцінну систему пошуку, 
яка будує **інвертований індекс** — структуру даних, що дозволяє миттєво знаходити документи за словами.

### M1: Побудова індексу
*   Створено модуль `index.py`, який за один прохід по корпусу будує:
    *   `postings: dict[str, list[Posting]]` — для кожного терміну відсортований список постінгів `(doc_id, tf)`.
    *   `doc_meta: dict[int, DocMeta]` — метадані документів (шлях, довжина).
*   Використано `@dataclass(frozen=True, slots=True)` для `Posting` та `DocMeta`.
*   Постінги збираються через `defaultdict(list)`.

### M2: Boolean-пошук
*   Створено модуль `search.py`, який підтримує запити з операторами:
    *   **AND** (неявний, через пробіл): `пошукова система`.
    *   **OR**: `пошукова or система`.
    *   **NOT**: `документ not система`.
*   Реалізовано два "двигуни" (поки що обидва використовують множини для простоти, але структура готова до
впровадження двовказівникового merge).

### M3: Збереження та завантаження
*   Створено модуль `store.py` з підтримкою двох форматів:
    *   **Pickle** (швидкий, але небезпечний для чужих файлів).
    *   **JSON** (безпечний, читабельний, але повільніший).
*   Додано CLI-команди:
    *   `python -m findex.index data/ --out index.bin` — побудова та збереження.
    *   `python -m findex.search index.bin "query"` — завантаження та пошук.

### M4: Вимірювання пам'яті
Проведено порівняння трьох варіантів зберігання постінгів на тому самому корпусі.

## Таблиця пам'яті (M4)

| Варіант зберігання постінгів | Пікова пам'ять (МБ) |
| :--- | :--- |
| Звичайний `@dataclass` (без slots) | 0.0266 |
| `@dataclass(frozen=True, slots=True)` | 0.0205 |
| `array('I')` (пари doc_id, tf) | 0.0345 |

**Пояснення:**
На такому малому корпусі (3 документи) різниця в пам'яті є мінімальною, оскільки накладні витрати на створення 
об'єктів `array` перевищують економію від відсутності об'єктів Python. Однак, при зростанні корпусу (до 
тисяч документів), картина зміниться:
*   Звичайний `@dataclass` створює для кожного об'єкта словник `__dict__`, що додає ~100 байтів на кожен 
екземпляр.
*   Використання `slots=True` прибирає цей словник, зменшуючи розмір об'єкта до розміру його полів
(економія 2-3 рази).
*   Варіант з `array('I')` взагалі не створює об'єктів Python для кожного постінгу, а зберігає дані як
сирі 4-байтові числа, що дає найбільшу економію пам'яті (до 9 разів на великих даних), але ускладнює код.

# Лабораторна 3: Рейтинг і модель об'єктів

## Що було зроблено

У цій лабораторній ми перетворили наш індекс на повноцінний об'єкт Python та додали ранжування результатів.

### M1: Рефакторинг у клас `Index`
*   Створено клас `Index`, який поводиться як незмінний словник (`Mapping`):
    *   `__getitem__`, `__iter__`, `__len__`, `__contains__` — доступ до постінгів.
    *   `__repr__` — зручне відображення.
    *   `num_docs`, `avg_doc_length` (`@cached_property`) — властивості.
    *   `df(term)` — document frequency.
*   Створено контекстний менеджер `open_index()` для безпечного завантаження індексу.

### M2: Ранжування (TF-IDF та BM25)
*   Створено протокол `Scorer` та дві його реалізації: `TfIdf` та `BM25(k1=1.5, b=0.75)`.
*   Результати пошуку повертаються як `SearchResult` (з полями `score`, `doc_id`, `snippet`), відсортовані
за спаданням оцінки.
*   Використовується `heapq.nlargest` для ефективного відбору топ-k.

### M4: Декоратори та сніпети

### Аналіз: GIL, процеси, закон Амдала та Python 3.13t

#### 1. Чому потоки під GIL не прискорили індексацію
Індексатор обмежений CPU: токенізація та оновлення Python-словників відбуваються для кожного документа. За увімкненого
GIL лише один потік виконує Python-байткод одночасно. На цьому корпусі 8 потоків повільніші за послідовну побудову
(0.1588 с проти 0.1270 с), а CPU-час зростає (0.2223 с проти 0.1270 с): потоки додають координаційні витрати, але
не додають паралельного виконання Python-коду.

#### 2. Процеси й ціна обходу GIL
Кожен процес має окремий інтерпретатор і GIL, тому CPU-час дочірніх процесів сумується, а Wall може бути коротшим за
цей сумарний CPU-час. Водночас macOS запускає процеси методом `spawn`: треба створити інтерпретатори, передати шляхи
та pickle-нути часткові індекси назад. На корпусі з 1003 невеликих файлів процеси не виграли: найкраще — 0.2201 с
на 4 процесах, усе ще повільніше за serial (0.1270 с). Parent RSS у таблиці не включає пам'ять воркерів, тож реальне
споживання всього дерева процесів вище. Тому серійний executor лишається типовим на цій машині й цьому корпусі.

#### 3. Де в часі `merge` проявляється закон Амдала
Згідно із законом Амдала, максимальне прискорення при розпаралелюванні на $N$ виконавців обмежене часткою коду $s$, 
яка виконується строго послідовно:

$$S(N) = \frac{1}{s + \frac{1 - s}{N}}$$

У цій реалізації `merge_indexes` послідовний і займає близько 3.6–5.6 мс. На free-threaded CPython чотири потоки
індексують за 0.0635 с; merge займає 4.85 мс, тобто близько 7.6% Wall time. Це одна з послідовних частин, що
обмежують прискорення за законом Амдала; на восьми потоках цей корпус уже повільніший, ніж на чотирьох.

#### 4. Що змінилося на Python 3.13t (без GIL) і гонитва даних
На CPython 3.13.18 free-threaded (`sys._is_gil_enabled() = False`) потоки виконують Python-код паралельно: чотири
потоки завершили індексацію за 0.0635 с — у 2.39 раза швидше за serial на тій самій збірці (0.1519 с). Вісім потоків
виявилися повільнішими за чотири; більше воркерів не гарантує кращої швидкодії.

Вимкнення GIL не робить складені операції атомарними. У демонстрації чотири потоки виконали 800 000 неатомарних
інкрементів: під GIL результат був 800 000, а в одному free-threaded прогоні — 461 804 (втрачено 338 196). У findex
часткові індекси не мають спільних словників: кожен воркер володіє локальним станом і наперед виділеним діапазоном
`doc_id`, а parent зливає результати після завершення. Для спільного лічильника потрібен `threading.Lock()`.

## Лабораторна робота 6: Асинхронний краулер, індексація та пошук

### Етика та дотримання правил обходу
Обхід проводився на спеціально призначеному відкритому навчальному ресурсі **`https://books.toscrape.com/`** 
(публічна пісочниця для тестування веб-краулерів, `robots.txt` якої дозволяє індексацію). 
Краулер ідентифікує себе чесним заголовком `User-Agent: findex-crawler/0.6 (+https://github.com/Evgeniy224/findex;
educational search engine lab)`, кешує та виконує правила `/robots.txt` для кожного хоста через `RobotsCache`, 
обмежує одночасність двома запитами на хост та паузою `0.2` секунди між запитами. Якщо `robots.txt` повертає помилку
сервера чи недоступний, хост закривається для обходу; `404` для самого `robots.txt` означає, що правил немає.

### Архітектура та ключові компоненти (`findex.crawler`)
* **HTTP-клієнт з таймаутами та повторами (`fetch.py`)**: `httpx.AsyncClient` із контролем часу очікування 
через `asyncio.timeout`, повторами лише на тимчасових збоях (`429`, `500`, `502`, `503`, `504`, 
таймаути та мережеві помилки) з exponential backoff + jitter і підтримкою заголовка `Retry-After`. 
Помилки `404` не повторюються; `Retry-After` не обрізається. Редирект перевіряється до наступного запиту: дозволені
лише редиректи на той самий host/port, і для кінцевого URL повторно перевіряється `robots.txt`.
* **Дотримання `robots.txt` (`robots.py`)**: асинхронний кеш `RobotsCache` на базі `urllib.robotparser.RobotFileParser` 
із блокуванням `asyncio.Lock` на хост для запобігання дублюючим запитам до `/robots.txt`; на помилках мережі та 5xx
обхід забороняється за замовчуванням.
* **Асинхронний генератор обходу (`crawl.py`)**: канонізація URL (`http/https`, нижній регістр схеми й хоста, 
видалення `#fragment`, нормалізація шляху, сортування query-параметрів), дедуплікація через `seen: set[str]`, 
черга `asyncio.Queue`, воркери під `asyncio.TaskGroup`, глобальний і per-host семафори та коректне скасування 
воркерів на `max_pages`. Резервування слотів не дозволяє зробити зайві успішні запити, а черга очищується під час зупинки.
* **Потокова інтеграція з CLI (`cli.py`, `corpus.py`, `index.py`)**: команда `findex crawl` пише сторінки у потоковий
JSONL по мірі надходження з живою панеллю метрик (`Rich Live`) та журналом `crawl.log`; файловий запис винесений через
`asyncio.to_thread`, мережеві запити асинхронні. Індексація виконується окремо поза циклом подій через `findex index`.

### Результати бенчмарку краулера (200 сторінок, однакові параметри ввічливості)

У кожному запуску: seed `https://books.toscrape.com/`, `--max-pages 200`, `--per-host 2`, `--delay 0.2`; змінювався лише
`--concurrency`. Повторити можна, наприклад, так:

```sh
uv run findex crawl https://books.toscrape.com/ --max-pages 200 --concurrency 1 --per-host 2 --delay 0.2 --out data/crawl_c1.jsonl --log crawl_c1.log
uv run findex crawl https://books.toscrape.com/ --max-pages 200 --concurrency 5 --per-host 2 --delay 0.2 --out data/crawl_c5.jsonl --log crawl_c5.log
uv run findex crawl https://books.toscrape.com/ --max-pages 200 --concurrency 20 --per-host 2 --delay 0.2 --out data/crawl_c20.jsonl --log crawl_c20.log
```

| `concurrency` | `per-host` | Сторінки | Помилки | Wall (s) | Pages/s | Speedup | Peak RSS (MB) |
| :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| 1 | 2 | 200 | 0 | 44.96 | 4.45 | 1.00x | 70.1 |
| 5 | 2 | 200 | 0 | 41.07 | 4.87 | 1.09x | 59.2 |
| 20 | 2 | 200 | 0 | 41.39 | 4.83 | 1.09x | 61.2 |

### Аналіз продуктивності та архітектурні висновки
1. **Що показав цей вимір:** asyncio дає змогу перекривати очікування мережі без окремого потоку на кожен запит, але
   concurrency 20 не прискорила цей ввічливо обмежений crawl відносно concurrency 5. Загальна швидкість уперлася у
   `--delay 0.2` і `--per-host 2`; це свідоме обмеження навантаження на сайт, а не свідчення, що asyncio не корисний.
   Для демонстрації вищої concurrency потрібен контрольований локальний mirror/сервер, не більший тиск на публічний сайт.
2. **Не блокувати цикл подій:** HTTP і robots-запити використовують async-клієнт, файлові записи відбуваються через
   `asyncio.to_thread`. CPU-індексація запускається окремо після crawl командою `findex index`.
3. **Перевірка 404:** новий benchmark не мав помилок, тому не приписуємо йому вигаданий рядок журналу. Натомість
   `tests/test_crawler.py::test_crawl_logs_404_once_and_continues` із `httpx.MockTransport` перевіряє, що 404 має
   `attempts=1`, `error="HTTP 404"` і не повторюється; окремий тест перевіряє блокування cross-host редиректу до
   відправлення запиту на інший host.
